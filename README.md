# NJU-Scheduler 项目文档：工作流、数据流与实现原理

> 本文写给编程初学者。读完后你应该能回答三个问题：**这个程序从哪里开始、中间经过了什么、最后到哪里结束**；**三个人各自负责哪一段、交接处传什么**；**每个模块内部大致在干什么**。代码细节不展开，但关键接口会写清楚“谁把什么传给谁”。

---

## 一、先用一句话认识这个项目

> 你给程序两张表（**已有课程表**和**待办任务表**），程序用模拟退火算法排出一张**一周计划表**，最后在网页上把这张表画出来。

输入两张表，输出一张表和一个网页。就这么简单。

```text
courses.txt ─┐
             ├──> [C 程序] ──> schedule.txt  (给人看)
tasks.txt   ─┘                schedule.json (给网页看)
                                    │
                                    v
                              viewer.html  (可视化)
```

---

## 二、项目里的三个“世界”

初学者最容易混乱的地方是：**同一个项目里其实有三个世界**，它们的数据形态不一样。

| 世界 | 里面有什么 | 谁住在里面 |
|---|---|---|
| **数据世界** | `Schedule` 结构体：7 天 × 96 格的二维表格 | A（IO 模块）负责把文本变成它 |
| **算法世界** | `cost()` 打分函数、`anneal()` 退火搜索 | C 负责在这里反复改表格、算分数 |
| **展示世界** | JSON 对象、HTML 页面、彩色方块 | B 负责把结构体变成 JSON，再变成网页 |

**三个世界之间的通道只有两个：**

1. 数据世界 → 展示世界：A 的 `export_schedule_json()` 把 `Schedule` 写成 JSON。
2. 数据世界 ↔ 算法世界：`cost()` 和 `anneal()` 直接读写 `Schedule` 内存，不需要序列化。

理解这一点，你就理解了整个架构。

## 三、时间槽：全项目统一的语言

所有模块内部**只使用“槽索引”**，不使用“小时”“分钟”这种浮点数。

| 约定 | 值 |
|---|---|
| 一天有多少槽 | 96（8:00–24:00，每 10 分钟一槽） |
| 一周有多少槽 | 7 × 96 = 672 |
| 槽 0 对应 | 周一 8:00–8:10 |
| 槽 95 对应 | 周日 23:50–24:00 |
| 熬夜区 | 每天槽 90–95（23:00–24:00） |

**换算公式只有两个：**

```text
槽索引 = (小时 - 8) × 6 + 分钟 ÷ 10
小时   = 8 + 槽索引 ÷ 6
分钟   = (槽索引 % 6) × 10
```

比如 `08:00` → 槽 0，`09:40` → 槽 10，`23:50` → 槽 95。

**为什么全项目统一用槽索引？** 因为如果用“小时 + 分钟”两个字段表示时间，比较大小、算时长、判断熬夜都要写额外逻辑；用一个整数槽索引，所有比较都变成普通的整数比较，不容易出错。

## 四、数据流全景：从文本到网页

下面这条路径是**一次完整运行**的全过程。每一步都标明“谁调用谁、传什么”。

### 第 1 步：B 启动程序

B 在命令行运行：

```text
scheduler.exe data\courses.txt data\tasks.txt out\
```

`main()` 接收到三个字符串参数：课程文件路径、任务文件路径、输出目录。

### 第 2 步：B 初始化一张空表

`main()` 在内存里建一个 `Schedule` 变量，把它的 672 个格子全部置为“空闲”（`task_index = -1`，`busy = 0`），任务数置 0。

> **关键点**：这张表就是后面所有模块共享的“画布”。A 在上面画课程，C 在上面摆任务，B 最后把它导出。

### 第 3 步：A 把课程画到表上

`main()` 调用 `load_existing_courses("data/courses.txt", &s)`，把表的地址传给 A 的读取函数。

A 的读取函数做三件事：

1. 打开文本文件，逐行读。
2. 把每一行的 `08:00`、`09:40` 用 `time_to_slot()` 换成槽索引。
3. 对 `[start_slot, end_slot)` 区间内的每个格子，把 `busy` 置 1。

> **注意**：课程的格子 `task_index` 仍然是 -1。这是区分“课程”和“任务”的核心规则——课程只看 `busy`，任务只看 `task_index`。

### 第 4 步：A 把任务读进来

`main()` 调用 `load_tasks("data/tasks.txt", &s)`。

A 的读取函数做四件事：

1. 逐行读任务名、时长（分钟）、截止日、截止时间、重要度。
2. 把分钟转成槽数：`duration_slots = 分钟 ÷ 10`。
3. 把截止时间转成槽索引：`deadline_slot = time_to_slot(...)`。
4. 把任务追加到 `s.tasks[]` 数组里，`s.task_count` 加 1。

> **注意**：读任务阶段**不把任务放进格子**。任务放哪里是 C 的退火算法决定的，A 只负责把任务记到任务清单里。

### 第 5 步：C 给当前表打一个初始分

`main()` 调用 `cost(&s)`，C 的 `cost` 函数接收表地址，返回一个 `double` 类型的数字（越小越好）。

这个数字被存进变量 `c0`，用于后面和优化后的分数对比。

### 第 6 步：C 的退火开始优化

`main()` 调用：

```text
anneal(s, 50000, 100.0, 0.9995, 0.01)
```

传进去五个参数：

| 参数 | 含义 |
|---|---|
| `s` | 初始计划表（已经有课程，任务还没摆） |
| `50000` | 最多迭代 5 万次 |
| `100.0` | 初始温度 |
| `0.9995` | 每轮降温系数 |
| `0.01` | 最低温度，低于它就停 |

`anneal` 返回一个**新的 `Schedule`**，被存进变量 `best`。这个新表里任务已经被摆到各个格子里了。

> **注意**：`anneal` 不会修改传进来的 `s`，它内部复制一份去折腾，最后返回最好的那一份。这样 `main` 里的原始数据不会被破坏。

### 第 7 步：C 给优化后的表再打一次分

`main()` 调用 `cost(&best)`，结果存进变量 `c1`。

现在 `main` 手里有三个关键数字：`c0`（初始分）、`c1`（最终分）、`best`（优化后的表）。

### 第 8 步：A 把结果导出成两种格式

`main()` 调用两次 A 的导出函数：

```text
export_schedule_txt(&best, "out/schedule.txt")
export_schedule_json(&best, "out/schedule.json", c0, c1)
```

第一个函数写一份**给人看的文本**：按天列出课程和任务、按任务汇总、统计信息。

第二个函数写一份**给网页看的 JSON**，同时还会生成一个 `web/viewer_data.js`，内容是：

```text
window.SCHEDULE_DATA = { ...JSON 内容... };
```

> **为什么多写一个 `.js` 文件？** 因为 Windows 上双击 HTML 打开时，浏览器不允许 JS 直接读取本地 JSON 文件（跨域限制）。但允许读取本地 JS 文件。所以 A 把 JSON 包一层变成 JS 变量赋值，B 的网页就能直接读。

### 第 9 步：B 在浏览器里打开网页

B 双击 `web/viewer.html`，浏览器加载：

1. `viewer.css`——决定页面长什么样。
2. `viewer_data.js`——提供数据。
3. `viewer.js`——读取数据，动态生成格子。

`viewer.js` 从 `window.SCHEDULE_DATA` 里拿到课程数组和任务数组，用 JS 画出 7 列 × 96 行的网格，把课程涂灰、任务按重要度上色、23:00 之后加红色斜纹。

至此，一次完整的数据流结束。

## 五、四个模块的实现原理

### 5.1 IO 模块（A 负责）：文本 ↔ 结构体

A 的工作可以概括成四句话：

- **读课程**：把 `[08:00, 09:40)` 这样的时间段变成 10 个连续格子的 `busy = 1`。
- **读任务**：把一行文本变成 `Task` 结构体，塞进 `s.tasks[]` 数组。
- **写文本**：把 `Schedule` 里散落在 672 个格子里的任务，按天、按任务两种视角重新组织成人类可读的文字。
- **写 JSON**：把 `Schedule` 转换成前端能直接用的对象，课程和任务分成两个数组。

**A 最需要小心的三件事：**

1. **边界**：`09:40` 对应槽 10，但它是结束时间，不占用槽 10。所以循环写 `for (slot = start; slot < end; slot++)`，不是 `<=`。
2. **校验**：`09:05` 这种不是 10 分钟对齐的时间必须报错，不能悄悄取整。
3. **初始化**：`task_index` 默认是 0，不是 -1。如果忘记把 672 个格子全置 -1，任务 0 会“幽灵般”占满全盘。这个 bug 非常隐蔽，务必在 `main` 初始化时就处理掉。

### 5.2 算法模块（C 负责）：给表打分 + 反复微调

这是全项目的“智能”所在。分成两个部分：

#### cost 函数：给一张表打分

`cost` 接收一个 `Schedule` 指针，返回一个 `double`。这个数字越小，说明这张表越“好”。

“好”由四个惩罚项加起来决定：

| 惩罚项 | 惩罚什么 | 大致量级 |
|---|---|---|
| 超 Deadline | 任务完成时间超过截止时间 | 超得越久、任务越重要，罚得越重 |
| 熬夜 | 23:00 之后还安排了任务 | 每格固定加一个比较大的数 |
| 碎片化 | 一天内的空闲/占用块太碎 | 连续 1–2 小时的块额外罚 |
| 重要度延迟 | 重要任务被排到越晚，罚得越多 | 重要度 × 第几天 |

**为什么用“惩罚”而不是“奖励”？** 因为模拟退火的自然形式是“找最小值”。把所有坏情况翻译成“加多少分”，最后总分最小的表就是最好的表。四个惩罚项之间的相对大小，就是调参时要平衡的东西。

#### anneal 函数：在表上反复微调

`anneal` 的原理可以类比成一个**在山谷里找最低点的人**：

1. 站在当前表的分数上，随机做一个**小改动**（比如把某个任务从周一下午挪到周二上午）。
2. 算新表的分数，比较新旧差值。
3. 如果变好了，就接受这个改动；如果变差了，**以一定概率也接受**——这个概率和“温度”有关。
4. 温度慢慢降低，接受“变差”的概率越来越小，最后几乎只接受变好的改动。
5. 记录整个过程中见过的最低分那张表，最后返回它。

“小改动”由一个叫 `random_neighbor` 的函数完成。它接收当前表和新表的指针，把当前表复制一份到新表，然后在副本上随机挪一个任务。

**为什么允许接受变差的改动？** 因为如果只接受变好的改动，很容易卡在“半山腰的小坑”里出不来。允许偶尔往上走一步，才有机会翻过小山脊，找到更深的山谷。温度高的时候往上走容易，温度低了就几乎不往上走。

**退火里的几个参数怎么影响结果：**

| 参数 | 变大 | 变小 |
|---|---|---|
| 初始温度 `T0` | 前期更“乱逛”，探索更广，但收敛慢 | 前期更保守，容易早熟 |
| 降温系数 `alpha` | 降温慢，搜索时间长，结果更稳 | 降温快，可能没搜完就冻住 |
| 最大迭代 `max_iter` | 搜索更充分，时间更长 | 可能没收敛 |
| 各惩罚权重 | 那个惩罚项被优先避免 | 那个惩罚项容易被忽略 |

调参的本质就是**在“结果好”和“跑得快”之间找平衡**，同时让四个惩罚项都得到适当照顾。

### 5.3 主程序（B 负责）：把所有模块串起来

`main.c` 本身逻辑很简单，就是一个**流水线**：

```text
打印作者信息
  -> 解析命令行参数
  -> 初始化空表
  -> 调 A 读课程
  -> 调 A 读任务
  -> 调 C 算初始分
  -> 调 C 退火
  -> 调 C 算最终分
  -> 调 A 导出 txt 和 json
  -> 结束
```

B 要保证的是：**顺序正确、每步检查返回值、出错时给出明确提示而不是崩溃。** 比如 `load_existing_courses` 返回 -1，`main` 应该打印“课程文件读取失败”并退出，而不是继续往下跑。

`main.c` 里唯一容易出错的地方是**初始化**：必须确保 `task_index` 全部是 -1，`busy` 全部是 0。如果 `main.c` 用 `memset` 把整个结构体清零，`task_index` 就变成 0 了——这是第一个大坑。

### 5.4 可视化（B 负责）：JSON → 彩色网格

B 的工作分两层：

**第一层：结构**。`viewer.html` 定义页面骨架：标题区、作者信息区、图例区、网格区、统计区。网格区先用 CSS Grid 画成 7 列（周一到周日）。

**第二层：渲染**。`viewer.js` 拿到 `window.SCHEDULE_DATA` 后，做三件事：

1. 遍历 `courses` 数组，把每个课程画成一个灰色块，位置由 `day`、`start`、`end` 决定。
2. 遍历 `tasks` 数组，对每个任务的 `assigned` 数组里每个时间段，画一个彩色块。颜色由 `importance` 决定。
3. 把所有数字指标（初始 cost、最终 cost、熬夜槽数等）填进统计区。

**B 最需要小心的两件事：**

1. **时间显示**：JSON 里的 `start` / `end` 是槽索引，网页上要显示成 `08:00` 这种格式，必须在 JS 里换算，不能指望 JSON 里存好时间字符串。
2. **同一任务多段**：一个任务可能被拆到周一下午和周二的上午，`assigned` 数组里有两个元素，网页上要画两个独立色块，用同一种颜色，不要硬连线。

## 六、三个人怎么配合：接口契约与联调

### 6.1 两个“宪法级”头文件

整个项目只有两个头文件是三人共享的：

- **`scheduler.h`**：定义 `Task`、`Slot`、`Schedule` 结构体，声明 `cost` 和 `anneal`。**只能由 C 修改**，改完必须通知 A 和 B 拉取。
- **`io.h`**：声明 A 的六个函数。**由 C 维护声明，A 实现**。

**任何人想加字段、改函数签名，必须先说、由 C 统一改、全员拉取。** 这是避免合并冲突最有效的方法。

### 6.2 交接处的“参数传递清单”

| 交接处 | 谁调用谁 | 传什么 | 返回什么 |
|---|---|---|---|
| 读课程 | `main` → `load_existing_courses` | 文件路径字符串 + `Schedule` 指针 | 0 成功 / -1 失败 |
| 读任务 | `main` → `load_tasks` | 文件路径字符串 + `Schedule` 指针 | 0 成功 / -1 失败 |
| 打分 | `main` → `cost` | `Schedule` 指针 | double 分数 |
| 退火 | `main` → `anneal` | 初始表、迭代上限、T0、alpha、Tmin | 新的 `Schedule`（按值返回） |
| 导出文本 | `main` → `export_schedule_txt` | 表指针 + 文件路径 | 0 / -1 |
| 导出 JSON | `main` → `export_schedule_json` | 表指针 + 文件路径 + 初始分 + 最终分 | 0 / -1 |
| 前端取数 | `viewer.js` ← `viewer_data.js` | 无参数，读取全局变量 `window.SCHEDULE_DATA` | 一个 JS 对象 |

注意 `anneal` 是**按值返回** `Schedule` 的。`Schedule` 结构体比较大（672 个格子 + 任务数组），按值返回会有一次拷贝开销，但在课程设计规模下完全没问题，换来的是接口最简洁——`main` 只需要写 `Schedule best = anneal(...)`，不用管内存分配。

### 6.3 Git 协作流程

**不要三个人直接改 `main` 分支。** 每人有自己的分支：

```text
main                 <- 稳定版本，只有 C 能合并
├── feature/io       <- A 写 io.c、io.h 实现
├── feature/main-web <- B 写 main.c、Makefile、viewer.*
└── feature/anneal   <- C 写 cost.c、anneal.c、调参
```

每天开工：

1. `git pull origin main` 拉最新。
2. `git checkout -b feature/xxx` 建自己的分支。
3. 写代码、自测、`git add` + `git commit`。
4. `git push origin feature/xxx`。
5. 在 GitHub 上开 Pull Request，描述里写“改了什么、怎么测的、有没有改 scheduler.h”。
6. C 审核后合并。

**合并顺序有讲究：**

1. C 先提交 `scheduler.h` 和 `io.h` 接口。
2. A 基于最新 `main` 实现 `io.c`，合并。
3. B 基于最新 `main` 写 `main.c` + `Makefile`，先把 `anneal` 调用临时注释掉，只测 IO 和导出，合并。
4. C 提交 `cost.c` + `anneal.c`，合并。
5. B 恢复 `anneal` 调用，跑全流程，写 `viewer.*`。
6. C 调参，A 按需补统计字段，B 更新演示脚本。

### 6.4 联调时的三个“必须一起看”

拿一份真实课程表 + 5 个任务，三人一起跑一次，逐项核对：

1. **JSON 字段对不对**：打开 `viewer_data.js`，看 `courses` 数组、`tasks[].assigned` 数组是不是和 `schedule.txt` 里写的一致。
2. **分数对不对**：`c0` 和 `c1` 是否打印，`c1` 是不是明显小于 `c0`。
3. **网页显示对不对**：课程灰色、任务彩色、23:00 后有红色区域、统计区数字和 `schedule.txt` 末尾一致。

## 七、几个初学者最容易误解的点

| 误解 | 正确理解 |
|---|---|
| “任务读进来就应该放到格子里” | 读任务只记录到 `tasks[]` 数组；放格子是退火的事 |
| “课程和任务都用 `busy=1` 表示占用” | 课程用 `busy=1`，任务用 `task_index>=0`，两者互斥 |
| “同一个任务的格子一定连续” | 任务可能被拆到多天，识别任务只能靠 `task_index`，不能靠连续性 |
| “网页可以直接 `fetch('schedule.json')`” | Windows 本地 `file://` 下会被浏览器拦截，必须用 `viewer_data.js` |
| “`anneal` 会修改传进去的表” | 它内部复制一份，返回新的表，原表不变 |
| “`cost` 返回的值可以是负数” | 四个惩罚项都是非负的，总分一般非负；如果出现负数，说明权重写错了 |
| “调参就是随便改数字” | 每次只改一个参数，记录指标，有对比才有结论 |

## 八、一句话总结

**A 把文本变成结构体、把结构体变回文本和 JSON；C 在结构体上反复微调、用加权惩罚打分；B 把结构体串成流水线、把 JSON 画成网页。三个人只通过 `scheduler.h`、`io.h`、`data/*.txt`、`out/*.json` 这四个契约交接，谁都不越界改别人的文件。** 理解这条主线的数据流，你就理解了这个项目。
