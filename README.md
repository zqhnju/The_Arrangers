  The_Arrangers
a program to optimize your schedule

# 项目文档：工作流、数据流与实现原理

> 本文写给编程初学者。读完后你应该能回答三个问题：**这个程序从哪里开始、中间经过了什么、最后到哪里结束**；**三个人各自负责哪一段、交接处传什么**；**每个模块内部大致在干什么**。代码细节不展开，但关键接口会写清楚“谁把什么传给谁”。

---

## 一、先用一句话认识这个项目

> 你给程序两张表（**已有课程表**和**待办任务表**），程序用模拟退火算法排出一张**一周计划表**，最后在网页上把这张表画出来。

输入两张表，输出一张表和一个网页。就这么简单。

```text
courses.txt ─┐
             ├──> [C 程序] ──> schedule.txt  (给人看)
tasks.txt   ─┘                schedule.json (给网页看)
                                    │
                                    v
                              viewer.html  (可视化)
```

---

## 二、项目里的三个“世界”

初学者最容易混乱的地方是：**同一个项目里其实有三个世界**，它们的数据形态不一样。

| 世界 | 里面有什么 | 谁住在里面 |
|---|---|---|
| **数据世界** | `Schedule` 结构体：7 天 × 96 格的二维表格 | A（IO 模块）负责把文本变成它 |
| **算法世界** | `cost()` 打分函数、`anneal()` 退火搜索 | C 负责在这里反复改表格、算分数 |
| **展示世界** | JSON 对象、HTML 页面、彩色方块 | B 负责把结构体变成 JSON，再变成网页 |

**三个世界之间的通道只有两个：**

1. 数据世界 → 展示世界：A 的 `export_schedule_json()` 把 `Schedule` 写成 JSON。
2. 数据世界 ↔ 算法世界：`cost()` 和 `anneal()` 直接读写 `Schedule` 内存，不需要序列化。

理解这一点，你就理解了整个架构。

## 三、时间槽：全项目统一的语言

所有模块内部**只使用“槽索引”**，不使用“小时”“分钟”这种浮点数。

| 约定 | 值 |
|---|---|
| 一天有多少槽 | 96（8:00–24:00，每 10 分钟一槽） |
| 一周有多少槽 | 7 × 96 = 672 |
| 槽 0 对应 | 每天 8:00–8:10 |
| 槽 95 对应 | 每天 23:50–24:00 |
| 熬夜区 | 每天槽 90–95（23:00–24:00） |

**换算公式只有两个：**

```text
槽索引 = (小时 - 8) × 6 + 分钟 ÷ 10
小时   = 8 + 槽索引 ÷ 6
分钟   = (槽索引 % 6) × 10
23:50 -> 95
24:00 -> 96（仅用于截止时间/结束边界）
```

比如 `08:00` → 槽 0，`09:40` → 槽 10，`23:50` → 槽 95。

**为什么全项目统一用槽索引？** 因为如果用“小时 + 分钟”两个字段表示时间，比较大小、算时长、判断熬夜都要写额外逻辑；用一个整数槽索引，所有比较都变成普通的整数比较，不容易出错。

### 1. 先理解“一张表”在内存里长什么样

程序里的 `Schedule` 就是一张**7 天 × 96 格的二维表格**，你可以把它想象成一张 Excel：

- **行**：一天里的 96 个 10 分钟时段。第 0 行是 8:00–8:10，第 1 行是 8:10–8:20，……，第 95 行是 23:50–24:00。
- **列**：一周 7 天。第 0 列是周一，第 6 列是周日。
- **每个格子**：要么空着，要么被课程占了，要么被任务占了。

```
             周一      周二      周三  ...  周日
08:00-08:10  [高数]    [空]      [空]       [空]
08:10-08:20  [高数]    [空]      [空]       [空]
...
23:50-24:00  [空]      [空]      [报告]     [空]
```

结构体就是把这张表以及“任务清单”打包在一起的一个变量。

---

### 2. 常量：全项目共享的数字

这些写在 `scheduler.h` 最上面，**所有模块都必须用这些名字，不许自己写 96、7、90 这种“魔法数字”**。

| 常量名 | 值 | 含义 | 为什么是这个值 |
|---|---|---|---|
| `DAYS` | 7 | 一周 7 天 | 固定 |
| `SLOTS_PER_DAY` | 96 | 一天 96 个 10 分钟槽 | 8:00 到 24:00 共 16 小时，16 × 6 = 96 |
| `SLOT_MINUTES` | 10 | 每个槽 10 分钟 | 你们定的粒度 |
| `START_HOUR` | 8 | 一天从 8:00 开始 | 假设 8 点前不排课 |
| `LATE_NIGHT_START` | 90 | 从第 90 槽开始算熬夜 | 8:00 + 90 × 10 分钟 = 23:00 |
| `MAX_TASKS` | 64 | 最多 64 个任务 | 数组容量上限，超过就报错 |
| `MAX_NAME` | 64 | 名字最长 63 字符 + 1 个结尾符 | 防止字符串溢出 |

**初学者常见误解**：`LATE_NIGHT_START = 90` 不是说“第 90 槽是熬夜”，而是说“**从第 90 槽开始到第 95 槽**都是熬夜区”。判断一个格子是不是熬夜，写 `slot >= LATE_NIGHT_START`。

### 3. `Task` 结构体：一个任务的全部信息

```c
typedef struct {
    char name[MAX_NAME];
    int  duration_slots;
    int  deadline_day;
    int  deadline_slot;
    int  importance;
} Task;
```

一个 `Task` 变量描述“**一件要做的事**”。比如“周五 23:50 前完成报告，需要 2 小时，很重要”。

#### 3.1 逐字段说明

| 字段 | 类型 | 含义 | 取值范围 | 谁写 | 谁读 |
|---|---|---|---|---|---|
| `name` | 字符数组 | 任务名字，比如“报告” | 最长 63 个字节 | A（读文件时写入） | A（导出）、B（网页显示） |
| `duration_slots` | 整数 | 这个任务**总共需要占多少个 10 分钟槽** | 正整数，一般 1~几百 | A（把分钟数 ÷ 10） | C（退火判断有没有排完）、A（统计） |
| `deadline_day` | 整数 | 截止时间是周几 | 0=周一，1=周二，……，6=周日 | A（读文件时写入） | C（算超时惩罚）、A（导出） |
| `deadline_slot` | 整数 | 截止时间在当天的第几个槽；96 表示当天 24:00 | 0~96 | A（把 `HH:MM` 换算成槽） | C（算超时惩罚）、A（导出） |
| `importance` | 整数 | 重要程度 | 1~5，5 最重要 | A（读文件时写入） | C（算重要度延迟惩罚）、B（决定颜色） |

#### 3.2 用一个例子串起来

假设 `tasks.txt` 里有一行：

```text
报告 120 4 23:50 5
```

A 读完以后，内存里就有这样一个 `Task`：

```
name           = "报告"
duration_slots = 12        （120 分钟 ÷ 10）
deadline_day   = 4         （周五）
deadline_slot  = 95        （23:50）
importance     = 5         （最重要）
```

C 在 `cost` 里就会检查：这个任务最后被安排在哪个槽？如果超过了“周五第 95 槽”这个时间点，就按“超了几槽 × 重要度 5”来罚分。

#### 3.3 初学者最容易误解的三点

**误解 1：“`duration_slots` 是任务最长能连续排多少槽。”**
不对。它是**总时长**。一个 12 槽的任务可以排成周一连续 12 槽，也可以拆成周一 6 槽 + 周二 6 槽。退火决定怎么拆。

**误解 2：“`deadline_slot = 95` 表示第 95 槽必须空着。”**
不准确。deadline_slot 是截止时刻所在槽，边界排他；95 表示 23:50 截止、slot95 不可用，96 表示 24:00 截止、slot95 可用。完整定义见 3.4。
**误解 3：“`importance` 只是用来显示颜色。”**
不对。它是 `cost` 里的权重。重要度 5 的任务超时 1 槽，罚分是重要度 1 的任务超时 1 槽的 5 倍。这也是为什么退火会优先把重要任务往前排。


---

### 3.4 deadline 的特殊性：为什么 `deadline_slot` 可以取 96

`Task` 里的 `deadline_day` 和 `deadline_slot` 不是两个独立字段，它们**联合表示一个绝对截止时刻**。理解这一点，才能理解为什么 `deadline_slot` 的范围是 `0~96` 而不是 `0~95`，以及为什么判断截止时不能写 `<=`。

#### 3.4.1 绝对时刻公式

```text
deadline_abs_exclusive = deadline_day * SLOTS_PER_DAY + deadline_slot
```

任务占用的任意一个槽，其绝对索引为：

```text
abs_index = day * SLOTS_PER_DAY + slot
```

**截止判断是排他的**：

```text
abs_index < deadline_abs_exclusive     /* 算截止前完成 */
abs_index >= deadline_abs_exclusive    /* 算超时 */
```

代码里 `cost.c` 必须写成：

```c
int deadline_abs_exclusive =
    s->tasks[i].deadline_day * SLOTS_PER_DAY
  + s->tasks[i].deadline_slot;

if (abs_index < deadline_abs_exclusive) {
    used++;   /* 截止前完成 */
}
```

不要写 `<=`，也不要先减 1 再比。`deadline_slot` 是**截止时刻所在槽**，不是“允许占用的最后一个槽”。

#### 3.4.2 `deadline_slot` 为什么能取 96

一天实际只有 96 个可占用槽，编号 `0~95`。但截止时刻可以落在 **24:00**，即当天结束、下一天开始的那一瞬间。为了表示这个边界，约定：

| `deadline_slot` | 含义 | 该槽能否被任务占用 |
|---:|---|---|
| `0` | 当天 08:00 截止 | 当天 slot0 及之后都不可用 |
| `1` | 当天 08:10 截止 | 当天 slot0 可用，slot1 及之后不可用 |
| `95` | 当天 23:50 截止 | 当天 slot0~94 可用，slot95 不可用 |
| `96` | 当天 24:00 截止 | 当天 slot0~95 全部可用 |

所以 `96` 不是一个真实的时间槽，而是**截止边界**。它只允许出现在 `deadline_slot` 和课程结束时间里，**不允许出现在任务实际占用的 `slot` 里**。任务实际占用的 `slot` 仍然只能是 `0~95`。

#### 3.4.3 24:00 与 00:00 的输入约定

`tasks.txt` 里表示“当天 24:00 截止”必须写 `24:00`，不能写 `00:00`：

- `24:00` → `deadline_slot = 96`，属于当天，表示“当天结束前完成”；
- `00:00` → 属于下一天，当前格式不支持跨天写法，应直接写成下一天的 `08:00`（`deadline_slot = 0`）。

A 的 `time_to_slot()` 对 `24:00` 只在“允许 24 点”的场合返回 `96`；解析任务开始时间、课程开始时间时不允许 `24:00`。

#### 3.4.4 周日 24:00 是合法上界

`deadline_day = 6`、`deadline_slot = 96` 时：

```text
deadline_abs_exclusive = 6 * 96 + 96 = 672 = 7 * 96
```

任务实际占用的最大绝对索引是 `6 * 96 + 95 = 671`，满足 `671 < 672`，所以“周日 24:00 截止”表示**整周所有槽都算截止前完成**。这是合法的，不需要特殊处理。

#### 3.4.5 常见错误

| 错误写法 | 后果 |
|---|---|
| `deadline_slot` 范围仍限制为 `0~95` | 无法表达 24:00 截止，slot95 永远不能用于当天截止 |
| `if (abs_index <= deadline_day*96 + deadline_slot)` | 多算一个槽，`deadline_slot=95` 时错误地允许 slot95 |
| `if (abs_index <= deadline_day*96 + deadline_slot - 1)` | 与上式等价，`deadline_slot=96` 时 slot95 会被错误排除 |
| 把 `deadline_slot=96` 当成真实槽写进 `slots[day][96]` | 数组越界，`SLOTS_PER_DAY` 仍是 96 |
| 任务输入写 `00:00` 表示当天 24:00 | 语义变成下一天 0:00，与“当天结束”混淆 |
| `used >= duration` 时仍加正惩罚 | 已完成任务反而被罚，与 deadline 语义无关但会掩盖 96 的效果 |

#### 3.4.6 一句话记住

> `deadline_day` 定天，`deadline_slot` 定边界；边界排他，`96` 表示当天 24:00；任务实际槽只能 `0~95`，`96` 只活在 deadline 和课程结束里。

### 4. `Slot` 结构体：一个格子的状态

```c
typedef struct {
    int busy;
    int task_index;
} Slot;
```

一个 `Slot` 描述“**某一个 10 分钟格子现在是什么状态**”。整个 `Schedule` 里有 7 × 96 = 672 个 `Slot`。

#### 4.1 逐字段说明

| 字段 | 含义 | 取值 | 说明 |
|---|---|---|---|
| `busy` | 这个格子是不是被**已有课程**占了 | 0 或 1 | 1 = 有课，不能排任务；0 = 没课 |
| `task_index` | 这个格子被**哪个任务**占了 | -1 或 0~63 | -1 = 空闲或课程；≥0 = 任务在 `tasks[]` 数组里的下标 |

#### 4.2 三种合法状态，只有三种

| 状态 | `busy` | `task_index` | 含义 |
|---|---|---|---|
| 空闲 | 0 | -1 | 可以放任务 |
| 课程 | 1 | -1 | 已上课，不能放任务 |
| 任务 | 0 | i（≥0） | 被第 i 个任务占用 |

**记住这张表，它是整个项目区分“课程”和“任务”的唯一依据。**

#### 4.3 为什么不用一个字段表示三种状态

初学者常问：“为什么不用 `state = 0/1/2` 表示空闲/课程/任务？”  
因为课程和任务可能在同一格冲突时需要分别判断，而且任务需要知道“是哪个任务”。两个字段各管一件事，比一个字段塞三种含义更清晰，也更不容易在导出和界面时搞混。

#### 4.4 用一个例子

假设周一 8:00–9:40 有“高等数学”，周一 10:00 开始排了“报告”的前 6 个槽（1 小时）：

```
slots[0][0]  = {busy=1, task_index=-1}   08:00 高数
slots[0][1]  = {busy=1, task_index=-1}   08:10 高数
...
slots[0][9]  = {busy=1, task_index=-1}   09:30 高数
slots[0][10] = {busy=0, task_index=-1}   09:40 空闲（高数结束）
slots[0][11] = {busy=0, task_index=-1}   09:50 空闲
slots[0][12] = {busy=0, task_index=0}    10:00 报告
slots[0][13] = {busy=0, task_index=0}    10:10 报告
...
slots[0][17] = {busy=0, task_index=0}    10:50 报告
slots[0][18] = {busy=0, task_index=-1}   11:00 空闲
```

注意：

- 高数占的是槽 0~9，**槽 10 是空的**，因为 09:40 是结束时间，不占格。
- 报告占槽 12~17，共 6 槽，说明“报告”这个任务在这里只排了一部分（总共需要 12 槽）。

### 5. `Schedule` 结构体：整个项目的“画布”

```c
typedef struct {
    Slot slots[DAYS][SLOTS_PER_DAY];
    Task tasks[MAX_TASKS];
    int  task_count;
} Schedule;
```

一个 `Schedule` 变量描述“**当前这张一周计划表的全部内容 + 所有任务的信息**”。

#### 5.1 逐字段说明

| 字段 | 类型 | 含义 | 谁写 | 谁读 |
|---|---|---|---|---|
| `slots` | 二维数组 `[7][96]` | 672 个格子的状态 | A 写课程格；C 写/清任务格 | A 导出、B 显示、C 打分 |
| `tasks` | 一维数组 `[64]` | 任务清单 | A 读文件时追加 | C 退火、A 导出、B 显示 |
| `task_count` | 整数 | 当前实际有几个任务 | A 每读一行加 1 | 所有人遍历任务时都用它 |

#### 5.2 为什么 `slots` 是二维数组

`slots[day][slot]` 两个下标直接定位：

- `slots[0][0]`：周一第 0 槽（周一 8:00–8:10）
- `slots[4][95]`：周五第 95 槽（周五 23:50–24:00）

如果写成一维数组 `slots[672]`，每次都要自己算 `day × 96 + slot`，容易错。二维数组让代码读起来和现实对应。

#### 5.3 为什么 `tasks` 和 `slots` 分开存

`tasks` 是“**要做什么**”，`slots` 是“**什么时候做**”。

- 任务的名字、时长、截止时间、重要度是**任务的固有属性**，不随排程变化，所以单独存一份。
- 任务被安排在哪些槽是**排程结果**，写在 `slots` 里。
- 两边通过 `task_index` 关联：`slots[0][12].task_index = 0` 表示“周一 10:00 这一格是 `tasks[0]` 这个任务”。

这种“属性表 + 时间表分开存”的设计，是排程类程序的标准做法。如果每个格子都存一份任务名和重要度，数据会大量重复，改一个任务属性要改很多格子。

#### 5.4 `task_count` 为什么不能省

因为 `tasks[64]` 只是容量上限，实际可能只有 3 个任务。遍历时必须写：

```c
for (int i = 0; i < s->task_count; i++)   /* 正确 */
```

不能写：

```c
for (int i = 0; i < MAX_TASKS; i++)       /* 错误，会读到未初始化的垃圾 */
```

`task_count` 是“任务清单里有几行有效数据”，和 Excel 里“实际行数”一个意思。

### 6. 初始化：三个必须一起做的动作

`Schedule` 刚声明出来时，内存里是随机垃圾值。**B 在 `main` 里必须做这三件事**，否则后面全错：

| 动作 | 为什么 |
|---|---|
| 所有 `slots[d][h].busy = 0` | 默认没有课 |
| 所有 `slots[d][h].task_index = -1` | 默认空闲 |
| `task_count = 0` | 任务清单还没读 |

**最危险的坑**：如果用 `memset(&s, 0, sizeof(s))` 清零，`task_index` 会变成 **0** 而不是 -1。后果是：整个棋盘上所有格子都“属于任务 0”，退火会以为任务 0 已经排满了，其他任务永远排不进去。这个 bug 不会崩溃，只会让结果诡异，非常难查。

**正确做法**：清零 `busy` 和 `task_count` 可以用 `memset`，但 `task_index` 必须用循环单独置 -1。

### 7. （可选扩展）如果决定在结构体里存课程名

上一份文档提到，当前 `Slot` 只存 `task_index`，**课程名没地方存**。如果组员 A 导出时想写“高等数学”而不只是“课程”，需要在 `scheduler.h` 里加：

```c
typedef struct {
    char name[MAX_NAME];
    int  day;
    int  start_slot;
    int  end_slot;
} Course;

typedef struct {
    Slot slots[DAYS][SLOTS_PER_DAY];
    Task tasks[MAX_TASKS];
    int  task_count;
    Course courses[MAX_COURSES];
    int  course_count;
} Schedule;
```

同时 `Slot` 加一个字段：

```c
typedef struct {
    int busy;
    int course_index;   /* -1=不是课程；>=0=课程数组下标 */
    int task_index;     /* -1=空闲；>=0=任务数组下标 */
} Slot;
```

| 新字段 | 含义 | 谁写 | 谁读 |
|---|---|---|---|
| `courses` | 课程清单，每门课一条记录 | A 读 `courses.txt` 时追加 | A 导出、B 显示 |
| `course_count` | 实际有几门课 | A | 所有人遍历课程时用 |
| `Slot.course_index` | 这一格属于哪门课 | A 读课程时写 | A 导出、B 显示 |

加了以后，课程格子的状态变成 `{busy=1, course_index=k, task_index=-1}`，导出时就能通过 `course_index` 找到课程名。

**代价**：`scheduler.h` 要改，A 的读取函数要改，B 的初始化要改，C 的 `cost` 不需要改（`cost` 不关心课程名）。**这件事必须由 C 统一改完通知全员拉取**，不能各改各的。

### 8. 一张图记住所有字段的关系

```text
Schedule
├── slots[7][96]          "什么时候"表
│   └── Slot
│       ├── busy          1=有课
│       ├── course_index  （可选）哪门课
│       └── task_index    -1=空；i=任务 i
│
├── tasks[64]             "做什么"表
│   └── Task
│       ├── name
│       ├── duration_slots    总共要几槽
│       ├── deadline_day      周几截止
│       ├── deadline_slot     当天第几槽截止
│       └── importance        1~5
│
└── task_count            实际有几个任务
```

**记住三句话：**

1. `slots` 管**时间**，`tasks` 管**属性**，`task_index` 是连接两者的**指针**。
2. 课程靠 `busy=1` 识别，任务靠 `task_index>=0` 识别，两者不能混。
3. 初始化时 `task_index` 必须是 -1，不是 0。

## 四、数据流全景：从文本到网页

下面这条路径是**一次完整运行**的全过程。每一步都标明“谁调用谁、传什么”。

### 第 1 步：B 启动程序

B 在命令行运行：

```text
scheduler.exe data\courses.txt data\tasks.txt out\
```

`main()` 接收到三个字符串参数：课程文件路径、任务文件路径、输出目录。

### 第 2 步：B 初始化一张空表

`main()` 在内存里建一个 `Schedule` 变量，把它的 672 个格子全部置为“空闲”（`task_index = -1`，`busy = 0`），任务数置 0。

> **关键点**：这张表就是后面所有模块共享的“画布”。A 在上面画课程，C 在上面摆任务，B 最后把它导出。

### 第 3 步：A 把课程画到表上

`main()` 调用 `load_existing_courses("data/courses.txt", &s)`，把表的地址传给 A 的读取函数。

A 的读取函数做三件事：

1. 打开文本文件，逐行读。
2. 把每一行的 `08:00`、`09:40` 用 `time_to_slot()` 换成槽索引。
3. 对 `[start_slot, end_slot)` 区间内的每个格子，把 `busy` 置 1。

> **注意**：课程的格子 `task_index` 仍然是 -1。这是区分“课程”和“任务”的核心规则——课程只看 `busy`，任务只看 `task_index`。

### 第 4 步：A 把任务读进来

`main()` 调用 `load_tasks("data/tasks.txt", &s)`。

A 的读取函数做四件事：

1. 逐行读任务名、时长（分钟）、截止日、截止时间、重要度。
2. 把分钟转成槽数：`duration_slots = 分钟 ÷ 10`。
3. 把截止时间转成槽索引：`deadline_slot = time_to_slot(...)`。
4. 把任务追加到 `s.tasks[]` 数组里，`s.task_count` 加 1。

> **注意**：读任务阶段**不把任务放进格子**。任务放哪里是 C 的退火算法决定的，A 只负责把任务记到任务清单里。

### 第 5 步：C 给当前表打一个初始分

`main()` 调用 `cost(&s)`，C 的 `cost` 函数接收表地址，返回一个 `double` 类型的数字（越小越好）。

这个数字被存进变量 `c0`，用于后面和优化后的分数对比。

### 第 6 步：C 的退火开始优化

`main()` 调用：

```text
anneal(s, 50000, 100.0, 0.9995, 0.01)
```

传进去五个参数：

| 参数 | 含义 |
|---|---|
| `s` | 初始计划表（已经有课程，任务还没摆） |
| `50000` | 最多迭代 5 万次 |
| `100.0` | 初始温度 |
| `0.9995` | 每轮降温系数 |
| `0.01` | 最低温度，低于它就停 |

`anneal` 返回一个**新的 `Schedule`**，被存进变量 `best`。这个新表里任务已经被摆到各个格子里了。

> **注意**：`anneal` 不会修改传进来的 `s`，它内部复制一份去折腾，最后返回最好的那一份。这样 `main` 里的原始数据不会被破坏。

### 第 7 步：C 给优化后的表再打一次分

`main()` 调用 `cost(&best)`，结果存进变量 `c1`。

现在 `main` 手里有三个关键数字：`c0`（初始分）、`c1`（最终分）、`best`（优化后的表）。

### 第 8 步：A 把结果导出成两种格式

`main()` 调用两次 A 的导出函数：

```text
export_schedule_txt(&best, "out/schedule.txt")
export_schedule_json(&best, "out/schedule.json", c0, c1)
```

第一个函数写一份**给人看的文本**：按天列出课程和任务、按任务汇总、统计信息。

第二个函数写一份**给网页看的 JSON**，同时还会生成一个 `web/viewer_data.js`，内容是：

```text
window.SCHEDULE_DATA = { ...JSON 内容... };
```

> **为什么多写一个 `.js` 文件？** 因为 Windows 上双击 HTML 打开时，浏览器不允许 JS 直接读取本地 JSON 文件（跨域限制）。但允许读取本地 JS 文件。所以 A 把 JSON 包一层变成 JS 变量赋值，B 的网页就能直接读。

### 第 9 步：B 在浏览器里打开网页

B 双击 `web/viewer.html`，浏览器加载：

1. `viewer.css`——决定页面长什么样。
2. `viewer_data.js`——提供数据。
3. `viewer.js`——读取数据，动态生成格子。

`viewer.js` 从 `window.SCHEDULE_DATA` 里拿到课程数组和任务数组，用 JS 画出 7 列 × 96 行的网格，把课程涂灰、任务按重要度上色、23:00 之后加红色斜纹。

至此，一次完整的数据流结束。

## 五、四个模块的实现原理

### 5.1 IO 模块（A 负责）：文本 ↔ 结构体

A 的工作可以概括成四句话：

- **读课程**：把 `[08:00, 09:40)` 这样的时间段变成 10 个连续格子的 `busy = 1`。
- **读任务**：把一行文本变成 `Task` 结构体，塞进 `s.tasks[]` 数组。
- **写文本**：把 `Schedule` 里散落在 672 个格子里的任务，按天、按任务两种视角重新组织成人类可读的文字。
- **写 JSON**：把 `Schedule` 转换成前端能直接用的对象，课程和任务分成两个数组。

**A 最需要小心的三件事：**

1. **边界**：`09:40` 对应槽 10，但它是结束时间，不占用槽 10。所以循环写 `for (slot = start; slot < end; slot++)`，不是 `<=`。
2. **校验**：`09:05` 这种不是 10 分钟对齐的时间必须报错，不能悄悄取整。
3. **初始化**：`task_index` 默认是 0，不是 -1。如果忘记把 672 个格子全置 -1，任务 0 会“幽灵般”占满全盘。这个 bug 非常隐蔽，务必在 `main` 初始化时就处理掉。

### 5.2 算法模块（C 负责）：给表打分 + 反复微调

这是全项目的“智能”所在。分成两个部分：

#### cost 函数：给一张表打分

`cost` 接收一个 `Schedule` 指针，返回一个 `double`。这个数字越小，说明这张表越“好”。

“好”由五个惩罚项和一个奖励项加起来决定。

#### anneal 函数：在表上反复微调

`anneal` 的原理可以类比成一个**在山谷里找最低点的人**：

1. 站在当前表的分数上，随机做一个**小改动**（比如把某个任务从周一下午挪到周二上午）。
2. 算新表的分数，比较新旧差值。
3. 如果变好了，就接受这个改动；如果变差了，**以一定概率也接受**——这个概率和“温度”有关。
4. 温度慢慢降低，接受“变差”的概率越来越小，最后几乎只接受变好的改动。
5. 记录整个过程中见过的最低分那张表，最后返回它。

“小改动”由一个叫 `random_neighbor` 的函数完成。它接收当前表和新表的指针，把当前表复制一份到新表，然后在副本上随机挪一个任务。

**为什么允许接受变差的改动？** 因为如果只接受变好的改动，很容易卡在“半山腰的小坑”里出不来。允许偶尔往上走一步，才有机会翻过小山脊，找到更深的山谷。温度高的时候往上走容易，温度低了就几乎不往上走。

**退火里的几个参数怎么影响结果：**

| 参数 | 变大 | 变小 |
|---|---|---|
| 初始温度 `T0` | 前期更“乱逛”，探索更广，但收敛慢 | 前期更保守，容易早熟 |
| 降温系数 `alpha` | 降温慢，搜索时间长，结果更稳 | 降温快，可能没搜完就冻住 |
| 最大迭代 `max_iter` | 搜索更充分，时间更长 | 可能没收敛 |
| 各惩罚权重 | 那个惩罚项被优先避免 | 那个惩罚项容易被忽略 |

调参的本质就是**在“结果好”和“跑得快”之间找平衡**，同时让四个惩罚项都得到适当照顾。

### 5.3 主程序（B 负责）：把所有模块串起来

`main.c` 本身逻辑很简单，就是一个**流水线**：

```text
打印作者信息
  -> 解析命令行参数
  -> 初始化空表
  -> 调 A 读课程
  -> 调 A 读任务
  -> 调 C 算初始分
  -> 调 C 退火
  -> 调 C 算最终分
  -> 调 A 导出 txt 和 json
  -> 结束
```

B 要保证的是：**顺序正确、每步检查返回值、出错时给出明确提示而不是崩溃。** 比如 `load_existing_courses` 返回 -1，`main` 应该打印“课程文件读取失败”并退出，而不是继续往下跑。

`main.c` 里唯一容易出错的地方是**初始化**：必须确保 `task_index` 全部是 -1，`busy` 全部是 0。如果 `main.c` 用 `memset` 把整个结构体清零，`task_index` 就变成 0 了——这是第一个大坑。

### 5.4 可视化（B 负责）：JSON → 彩色网格

B 的工作分两层：

**第一层：结构**。`viewer.html` 定义页面骨架：标题区、作者信息区、图例区、网格区、统计区。网格区先用 CSS Grid 画成 7 列（周一到周日）。

**第二层：渲染**。`viewer.js` 拿到 `window.SCHEDULE_DATA` 后，做三件事：

1. 遍历 `courses` 数组，把每个课程画成一个灰色块，位置由 `day`、`start`、`end` 决定。
2. 遍历 `tasks` 数组，对每个任务的 `assigned` 数组里每个时间段，画一个彩色块。颜色由 `importance` 决定。
3. 把所有数字指标（初始 cost、最终 cost、熬夜槽数等）填进统计区。

**B 最需要小心的两件事：**

1. **时间显示**：JSON 里的 `start` / `end` 是槽索引，网页上要显示成 `08:00` 这种格式，必须在 JS 里换算，不能指望 JSON 里存好时间字符串。
2. **同一任务多段**：一个任务可能被拆到周一下午和周二的上午，`assigned` 数组里有两个元素，网页上要画两个独立色块，用同一种颜色，不要硬连线。

## 六、三个人怎么配合：接口契约与联调

### 6.1 两个“宪法级”头文件

整个项目只有两个头文件是三人共享的：

- **`scheduler.h`**：定义 `Task`、`Slot`、`Schedule` 结构体，声明 `cost` 和 `anneal`。**只能由 C 修改**，改完必须通知 A 和 B 拉取。
- **`io.h`**：声明 A 的六个函数。**由 C 维护声明，A 实现**。

**任何人想加字段、改函数签名，必须先说、由 C 统一改、全员拉取。** 这是避免合并冲突最有效的方法。

### 6.2 交接处的“参数传递清单”

| 交接处 | 谁调用谁 | 传什么 | 返回什么 |
|---|---|---|---|
| 读课程 | `main` → `load_existing_courses` | 文件路径字符串 + `Schedule` 指针 | 0 成功 / -1 失败 |
| 读任务 | `main` → `load_tasks` | 文件路径字符串 + `Schedule` 指针 | 0 成功 / -1 失败 |
| 打分 | `main` → `cost` | `Schedule` 指针 | double 分数 |
| 退火 | `main` → `anneal` | 初始表、迭代上限、T0、alpha、Tmin | 新的 `Schedule`（按值返回） |
| 导出文本 | `main` → `export_schedule_txt` | 表指针 + 文件路径 | 0 / -1 |
| 导出 JSON | `main` → `export_schedule_json` | 表指针 + 文件路径 + 初始分 + 最终分 | 0 / -1 |
| 前端取数 | `viewer.js` ← `viewer_data.js` | 无参数，读取全局变量 `window.SCHEDULE_DATA` | 一个 JS 对象 |

注意 `anneal` 是**按值返回** `Schedule` 的。`Schedule` 结构体比较大（672 个格子 + 任务数组），按值返回会有一次拷贝开销，但在课程设计规模下完全没问题，换来的是接口最简洁——`main` 只需要写 `Schedule best = anneal(...)`，不用管内存分配。

### 6.3 Git 协作流程

**不要三个人直接改 `main` 分支。** 每人有自己的分支：

```text
main                 <- 稳定版本，只有 C 能合并
├── feature/io       <- A 写 io.c、io.h 实现
├── feature/main-web <- B 写 main.c、Makefile、viewer.*
└── feature/anneal   <- C 写 cost.c、anneal.c、调参
```

每天开工：

1. `git pull origin main` 拉最新。
2. `git checkout -b feature/xxx` 建自己的分支。
3. 写代码、自测、`git add` + `git commit`。
4. `git push origin feature/xxx`。
5. 在 GitHub 上开 Pull Request，描述里写“改了什么、怎么测的、有没有改 scheduler.h”。
6. C 审核后合并。

**合并顺序有讲究：**

1. C 先提交 `scheduler.h` 和 `io.h` 接口。
2. A 基于最新 `main` 实现 `io.c`，合并。
3. B 基于最新 `main` 写 `main.c` + `Makefile`，先把 `anneal` 调用临时注释掉，只测 IO 和导出，合并。
4. C 提交 `cost.c` + `anneal.c`，合并。
5. B 恢复 `anneal` 调用，跑全流程，写 `viewer.*`。
6. C 调参，A 按需补统计字段，B 更新演示脚本。

### 6.4 联调时的三个“必须一起看”

拿一份真实课程表 + 5 个任务，三人一起跑一次，逐项核对：

1. **JSON 字段对不对**：打开 `viewer_data.js`，看 `courses` 数组、`tasks[].assigned` 数组是不是和 `schedule.txt` 里写的一致。
2. **分数对不对**：`c0` 和 `c1` 是否打印，`c1` 是不是明显小于 `c0`。
3. **网页显示对不对**：课程灰色、任务彩色、23:00 后有红色区域、统计区数字和 `schedule.txt` 末尾一致。

## 七、几个初学者最容易误解的点

| 误解 | 正确理解 |
|---|---|
| “任务读进来就应该放到格子里” | 读任务只记录到 `tasks[]` 数组；放格子是退火的事 |
| “课程和任务都用 `busy=1` 表示占用” | 课程用 `busy=1`，任务用 `task_index>=0`，两者互斥 |
| “同一个任务的格子一定连续” | 任务可能被拆到多天，识别任务只能靠 `task_index`，不能靠连续性 |
| “网页可以直接 `fetch('schedule.json')`” | Windows 本地 `file://` 下会被浏览器拦截，必须用 `viewer_data.js` |
| “`anneal` 会修改传进去的表” | 它内部复制一份，返回新的表，原表不变 |
| “调参就是随便改数字” | 每次只改一个参数，记录指标，有对比才有结论 |

## 八、一句话总结

**A 把文本变成结构体、把结构体变回文本和 JSON；C 在结构体上反复微调、用加权惩罚打分；B 把结构体串成流水线、把 JSON 画成网页。三个人只通过 `scheduler.h`、`io.h`、`data/*.txt`、`out/*.json` 这四个契约交接，谁都不越界改别人的文件。** 理解这条主线的数据流，你就理解了这个项目。
